# Right-sized tasks and continuous autonomous dispatch

Read before creating the episode's implementation tasks. The initial migration needed dozens of family workers. A weekly delta should scale to **actual changed behavior and consumers**, not repeat that fleet or accumulate one enormous foundation session.

## Task sizing rule

A task should fit one fresh worker's focused context and produce one reviewable patch plus meaningful regression evidence. Prefer roughly one focused implementation session (often 30–90 minutes), not a promise to fix everything in a subsystem. Estimate from behavior/seams and source tests, not line counts alone.

| Delta | Sensible unit |
|---|---|
| Tiny pure helper/default adjustment, obvious test | Coordinator patch or one small task; do not create an epic/file-worker swarm |
| One component interaction change | One family owner, including affected parts and tests |
| Coupled Checkbox/Group or Radio/Group change | One atomic owner when transactions/registration cannot be separated safely |
| Shared merge/cancellation contract used by many triggers | One event-seam owner; targeted real consumers as evidence; no duplicate fix per family |
| Ref/hydration namespace defect | One renderer/ref/hydration owner; separate read-only qualification if useful |
| Independent portal logical ancestry and geometry change | Separate owners only when files/contracts are disjoint |
| New export/signature plus component logic | Component implementation first; central barrel/declaration/manifest owner integrates |
| Many docs examples changed | One stable demo convention, disjoint family/variant workers; one catalog writer |
| Toolchain/compiler bump plus behavior change | Separate toolchain qualification from port logic; do not let each worker update lockfiles |
| Unrelated bug discovered during reconciliation | New linked narrow follow-up; not unlimited expansion of the original worker |

Do not split one changing file by line ranges. Do not give multiple family agents permission to patch a shared helper. Do not allocate epics as worker assignments.

## Map changed behavior before counting agents

1. Read old/new source and tests for the change; use source mappings to locate target.
2. Identify the smallest shared owner when multiple families fail from one cause.
3. Determine the public contract changes, necessary dependent edits, and independent consumers.
4. Give each task exact allowlisted files and one acceptance boundary.
5. Add dependencies only for actual missing contracts/runtime requirements, not a global “all foundations complete” barrier.

Static reverse imports are useful, but inspect context providers, aliases, copied algorithms, type augmentation, source tabs and dynamic registries. A shared focus delta may require a real Menu/Popover regression even when the source diff touched one file.

If the proposed task owns renderer + refs + floating + forms + all consumers, split it. If it needs a whole-project rediscovery to begin, the brief is missing source paths/contracts. If its planned output is mostly mapping JSON, shrink the administration and start implementation.

## Shared-file owners

Assign explicitly for the episode, using current Beads `owns` and existing project structure:

- Source state, locks, episode records and promotion: coordinator/maintenance engine owner only.
- Root package/workspace/lock/config: one integrator.
- Public root/type/floating facades and export contract: one integration owner.
- Declaration/build generators and their outputs: disjoint types/runtime owners; runtime clean must not remove types.
- Shared foundation leaf: one runtime owner.
- Docs intake/semantic overlays, API output, demo runtime/catalog, site shell, authored family examples: separate boundaries.

Ownership metadata can be incomplete or historical. Investigate and explicitly coordinate a needed extension; do not invent an overlapping utility to avoid it. A simple seam request should be resolved promptly, not become days of routing bureaucracy.

## Contract readiness

The initial port used typed holes by explicit user override. That was concurrent design-time development, not validated prerequisites. **Default for maintenance: use existing real APIs; land changed shared contracts before dependent implementation that requires them.**

If deliberate interface-first parallelism is requested:

- freeze exact signatures/ownership and identify which functions are unimplemented;
- workers may author against that contract without modifying it;
- do not close runtime-dependent acceptance on a typecheck or throwing scaffold;
- coordinate runtime replay once the real implementation lands.

Avoid ambiguous APIs that hide staged semantics: name accepted-transaction trigger lookup separately from committed state; distinguish open/mounted/readiness; represent raw element access explicitly. Source-equivalent capabilities matter more than hook names.

## Standalone worker brief

Each Beads task/dispatch must carry:

```text
Episode: source + full from/to SHAs + report identity + relevant oracle/runtime pin.
Behavior: upstream change and required observable effect.
Read: exact old/new implementation, test/spec, target and shared API paths.
Method: load user-level react-to-solid-v2-port; copy new files literally before adapting;
        preserve source-shaped algorithms/types/JSDoc and each original test case;
        apply old/new deltas to existing Solid files without recopying over them.
Own: exclusive target files/directories; shared integration owner named.
Consume: stable API signatures, prior dependency handoff and staged-write rules.
Implement: complete bounded change, including source-defined difficult edge cases.
Verify: smallest real regression, related suite/types, required native/SSR/consumer checks.
Do not: source edits, duplicated helpers, root-file races, weakened diagnostics/assertions.
Escalate: exact shared defect/request with file/function/repro and continue independent work.
Handoff: short source-backed changes, actual checks, remaining defects/gates.
Terminal: RTK everywhere; no ccc indexing/init/refresh; no commits/publication.
```

Forward reviewer findings verbatim where useful. Do not require a worker to recover the entire old migration chat before fixing a known bug. Read the relevant reference once; provide the working solution/root cause already established.

## Continuous dispatch and review

Claim executable tasks, dispatch all safely disjoint work up to actual capacity, and replenish as each handoff arrives. No arbitrary two/three-agent ceiling; also no “tens of agents” target for a two-function delta.

As a worker finishes:

1. Inspect its changes against actual old/new source and retained source tests; “done” or a green rewritten suite alone is insufficient. Check for invented algorithms, broadened type constraints, lost branches/JSDoc, condensed scenarios and public fixtures replaced by internal probes. Required Solid lifecycle adaptation is legitimate; optional redesign is not implicitly authorized.
2. Resolve central integration requests under their owner.
3. Run/inspect the smallest acceptance evidence needed; distinguish inventory counts from behavior.
4. Mark only verified scope complete and launch newly unblocked work immediately.
5. Use a fresh reviewer/fixer for high-risk seams when warranted, not automatic duplicate review of every unchanged component.

Source-fingerprint qualification happens after writers stop. Parallel diagnosis/results remain useful but cannot be final evidence if code changed during the run.

## Stop context runaway

The initial shared reviewer became an extremely large conversation. That was an orchestration failure, not a pattern to retain.

When a worker accumulates unrelated tasks, repeats broad exploration, or has materially outgrown its brief:

1. Request **one bounded handoff**: current defects, exact files/functions, reproduction, proven cause versus hypothesis, existing unfinished edits, exclusive next scope.
2. Stop its implementation; do not continue issuing more broad fixes into that chat.
3. Split independent remaining causes among fresh narrow workers. Keep renderer/ref ownership together when coupled.
4. Recover history through targeted recall only if the handoff lacks an essential fact.

A cancellation is different: discover the existing child, inspect applied edits, and resume its bounded assignment when appropriate. Do not launch a duplicate writer on the same scope.

## Blockers without bureaucracy

Keep missing interactions, unsafe ownership, and uncertain required APIs implementation-blocking. Tooling-only follow-ups may split completed implementation scope, with explicit acceptance adjustment and affected gate dependency.

A deferred issue needs originating task/range, affected components, exact files/command, observed evidence, classification, remaining work/acceptance and gate. Reuse the actual issue for a root cause instead of one duplicate per affected family. Correct retracted diagnoses in the same place.

Do not spend the whole delta moving tickets. Enough tracking to resume and qualify is the goal; the patch and source regression are the work.
