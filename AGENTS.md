## Mandatory copy-first migration and maintenance
- Before porting, re-porting, reviewing source fidelity, or reconciling upstream changes to implementation, tests, docs, examples, or tooling, load the user-level **`react-to-solid-v2-port`** skill. If the harness does not advertise it, read `~/.config/opencode/skills/react-to-solid-v2-port/SKILL.md` directly and its task-relevant references. If unavailable, report that explicitly; these project rules still apply. Pass the skill requirement and these rules to every delegated worker. For weekly deltas, also load project `maintain-from-source`; for reactive work, additionally load `solid-v2-runtime` as required below.
- **Copy first, adapt minimally.** For a new ported file or an explicitly requested re-port, literally copy the pinned canonical source with the terminal (`rtk proxy cp`, or the skill's no-overwrite copy helper), including its tests/helpers/notices, into the authorized target or staging area. Do not recreate it from a description or remembered behavior. Inspect destinations before copying; never overwrite existing user work or Solid adaptations indiscriminately.
- Keep source-corresponding organization, algorithms, branches, defaults, arithmetic, public type constraints, JSDoc and notices wherever they are framework-independent. Limit edits to necessary Solid 2 semantics and explicitly requested behavior changes. Do not compress/reorganize code or invent a new state machine, configuration model or generic engine merely because it is easier to generate. Explain any substantial structural deviation with the source requirement and a specific Solid constraint; obtain explicit approval for optional architectural redesign.
- For maintenance, compare immutable old/new React source with the existing Solid counterpart and port the actual delta. Preserve established native adaptations; do not recopy the entire upstream tree over owned files. New upstream files follow copy-first. A source-shaped re-port of existing code requires explicit scope, not automatic replacement because a diff looks different.
- Preserve the original source test scenarios, parameters, fixtures, assertions and generated conformance registrations. Adapt their framework execution rather than replacing large suites with representative cases, combining distinct scenarios, substituting core fixtures for public integration, or dropping hard cases. React-only cases need a specific justified adaptation/exclusion; added Solid ownership/hydration/performance tests supplement the originals. A green custom suite or a source-path comment is not proof the original suite was migrated.
- Apply the same discipline to documentation: copy the real versioned layout/theme/components, prose, CSS/assets and examples, then adapt the necessary runtime/serving seams. Do not replace the source website with an invented shell and call it faithful. Check executed imports across workspace/dependency boundaries; not all upstream support code lives under the apparent docs directory.
- Report code correspondence separately from tested behavioral parity. Do not call a heavily reconstructed subsystem an "almost exact" source migration merely because selected tests pass. Do not assume a necessary native lifecycle change is a behavior defect merely because the text differs.

## Test reporting terminology — mandatory for all agents
- A case excluded from one suite but executed in another is **lane-routed**, not skipped. Say **"executed in the browser lane"**, **"executed in the SSR lane"**, or name its actual execution lane.
- Never present a runner's raw `skipped` total as a count of untested cases. Separate verified execution in another lane, cases awaiting execution, genuinely unexecuted skips, and unsupported platform/capability exclusions. Keep raw runner counts in evidence, explicitly labeled as runner accounting.
- Claim execution in another lane only when the corresponding case has execution evidence. An authored test or a green suite total alone does not establish that correspondence.
- Apply this terminology in user responses, reports, ledgers and handoffs, and pass this rule to any delegated agents. Keep missing/partial source coverage separate from lane routing.

## Implementation
- The initial migration allowed family-parallel development against typed scaffolds; that was a historical execution override, not the default maintenance method. Use existing real contracts, bounded coherent tasks and single-owned shared files. Do not restart a whole fleet or build a new scaffold architecture around a small delta. Prioritize production code and copied source tests over tracking overhead; scaffold-only checks cannot establish implementation completion.
- React outcomes and test assertions are canonical; React lifecycle machinery is not.
- Use Solid 2 accessors/memos, draft stores, direct context providers, split effects and setup-owned resources. No React hook emulation or Solid 1 imports.
- Native events retain Base UI cancellation, reason and callback-order contracts. `preventDefault`, `preventBaseUIHandler` and `details.cancel` are different operations.
- Browser tests are authored/retained during porting but their full execution belongs to final qualification. A green jsdom suite does not close deferred browser coverage.
- Record source-to-target and test mappings, exact checks, adaptations and outstanding browser cases in the ticket-owned tracking files. Never assert bug-free parity from a type check alone.
- Before closing a ticket, run its available checks and verify its acceptance criteria. New findings become blocked child tickets, not silent omissions.

Pin and track its immutable source separately and reconcile updates on developer request, alongside Base UI. Owned adaptations must satisfy Solid 2 RC13 and Base UI behavior; donor APIs do not override either contract. Preserve license/provenance. Assess other small React-only dependencies individually: tracked donor for substantial maintained logic, licensed one-time adaptation for genuinely tiny helpers.
